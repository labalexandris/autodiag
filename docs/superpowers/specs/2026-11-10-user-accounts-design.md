# Λογαριασμοί χρηστών και ρόλοι

Ημερομηνία: 2026-11-10

## Στόχος

Αντικατάσταση του κοινού `ADMIN_PASSWORD` με προσωπικούς λογαριασμούς για τους δύο ιδιοκτήτες και τον υπάλληλο, με ρόλους και διαχείριση χρηστών μέσα από την εφαρμογή. Οι χρήστες αποθηκεύονται στο Neon ώστε να μη χάνονται σε deploy. Τα υπόλοιπα δεδομένα (ραντεβού, πελάτες κ.λπ.) μένουν προς το παρόν στα mock και μεταφέρονται σε επόμενο βήμα.

## Ρόλοι

| | Ιδιοκτήτης (`owner`) | Υπάλληλος (`staff`) |
|---|---|---|
| Σήμερα, Ημερολόγιο, Πελάτες, Ρυθμίσεις | ναι | ναι |
| Επιβεβαίωση, μετακίνηση, έναρξη, ολοκλήρωση ραντεβού, εργασίες βιβλιαρίου | ναι | ναι |
| Αναφορές | ναι | όχι (ούτε μενού, ούτε σελίδα: redirect στο /admin) |
| Απόρριψη / ακύρωση ραντεβού (`cancelled`) | ναι | όχι (κρυμμένο κουμπί + έλεγχος στο server action) |
| Διαχείριση χρηστών | ναι | όχι |
| Αλλαγή δικού του κωδικού | ναι | ναι |

## Αρχικοί χρήστες

Δημιουργούνται αυτόματα όταν ο πίνακας είναι άδειος:

- `manolis` / `123`, Μανώλης Παπουτσάκης, owner
- `dimitris` / `123`, Δημήτρης Κωτσάς, owner

Ο υπάλληλος προστίθεται από την εφαρμογή. Δεν υπάρχει υποχρεωτική αλλαγή κωδικού (απόφαση ιδιοκτήτη).

## Δεδομένα

Πίνακας `users` στο Neon (δημιουργείται με `CREATE TABLE IF NOT EXISTS` στην πρώτη χρήση):

- `id` uuid PK
- `username` text unique (πεζά, χωρίς κενά)
- `name` text
- `role` text: `owner` | `staff`
- `password_hash` text: scrypt (node:crypto) με τυχαίο salt, μορφή `salt:hash`
- `active` boolean
- `created_at` timestamptz

Πρόσβαση μόνο μέσω `src/lib/users.ts` (driver `@neondatabase/serverless`).

## Σύνδεση και session

- `/login`: όνομα χρήστη + κωδικός. Σε λάθος, γενικό μήνυμα και καθυστέρηση ~600ms.
- Cookie `ad_session` (httpOnly, sameSite lax, secure σε production, 30 ημέρες) με `userId.expiry.υπογραφή`. Υπογραφή HMAC-SHA256 με `SESSION_SECRET`.
- `proxy.ts`: ελέγχει μόνο την υπογραφή και τη λήξη (χωρίς βάση).
- `requireUser()` / `requireOwner()` στον server: διαβάζουν τον χρήστη από τη βάση σε κάθε σελίδα/ενέργεια admin. Ανενεργός ή διαγραμμένος χρήστης → αποσύνδεση. Έτσι η απενεργοποίηση και η αλλαγή ρόλου ισχύουν αμέσως.
- Κατάργηση `ADMIN_PASSWORD` και του «ανοιχτού admin χωρίς κωδικό». Χωρίς `DATABASE_URL` / `SESSION_SECRET` η εφαρμογή δείχνει σαφές μήνυμα σφάλματος στο login.

## Διεπαφή

- Μενού: εμφανίζει όνομα και ρόλο του συνδεδεμένου χρήστη. Οι Αναφορές κρύβονται για τον υπάλληλο (sidebar και κάτω μπάρα κινητού).
- Μενού χρήστη: «Αλλαγή κωδικού» (τρέχων + νέος, ελάχιστο 3 χαρακτήρες) και «Αποσύνδεση».
- Ρυθμίσεις → ενότητα «Χρήστες» (μόνο owner):
  - λίστα με όνομα, username, ρόλο, ενεργός/ανενεργός
  - «Νέος χρήστης»: όνομα, username, ρόλος, κωδικός
  - επεξεργασία: όνομα, ρόλος, νέος κωδικός (προαιρετικό), ενεργός
  - κανόνας: πρέπει να μένει πάντα τουλάχιστον ένας ενεργός owner· ένας owner δεν μπορεί να απενεργοποιήσει ή να υποβιβάσει τον εαυτό του αν είναι ο τελευταίος

## Ρυθμίσεις περιβάλλοντος

- `DATABASE_URL` (Neon, pooled connection string)
- `SESSION_SECRET` (τυχαίο, ≥32 χαρακτήρες· στο Render `generateValue: true`)
- αφαιρείται το `ADMIN_PASSWORD` από `render.yaml` και `.env.example`

## Έλεγχος

Playwright τεστ σε τοπικό production build με την πραγματική βάση:

1. login owner → βλέπει Αναφορές και Χρήστες, δημιουργεί υπάλληλο
2. login υπάλληλος → δεν βλέπει Αναφορές, το `/admin/reports` κάνει redirect, δεν υπάρχει Απόρριψη/Ακύρωση, μπορεί να επιβεβαιώσει
3. owner απενεργοποιεί τον υπάλληλο → η επόμενη σελίδα του υπαλλήλου τον βγάζει στο login
4. λάθος κωδικός → μήνυμα σφάλματος
5. ο δοκιμαστικός υπάλληλος διαγράφεται απευθείας από τη βάση στο τέλος του τεστ (η εφαρμογή δεν έχει διαγραφή, μόνο απενεργοποίηση)
